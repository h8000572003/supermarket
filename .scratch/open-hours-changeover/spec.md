# 規格：營業中換貨

Status: ready-for-agent

詞彙以 `CONTEXT.md` 為準（換貨、下架、格位、陳列庫存、補貨門檻、派工）；架構決策見 ADR 0001、0002、0004（修訂 ADR 0003）。

## Problem Statement

格位的商品只能在準備階段指定。營業中，店長發現某個格位擺的是賣不動的商品，或某個類別一直缺貨想多開一格，都只能等到隔天。整個營業時段格位被冷門商品佔住，店長看得到問題卻無計可施。

如果讓格位在營業中立即換成新商品，又會出現 ADR 0003 想避免的狀況：顧客正走向的格位、店員正要補的格位，商品突然變了。

## Solution

營業中也能更換格位的商品，但由店員逐步完成，不會立即改變：

1. 店長在格位面板選新商品，格位進入換貨。
2. 店員來之前，舊商品留在架上照賣。
3. 店員來**下架**：一趟取下這格全部的舊商品。取下的那一刻，格位改成新商品而且是空的；舊商品搬回倉庫。
4. 新商品照一般補貨上架。

打烊時還沒換完的直接完成。準備階段更換格位商品仍然立即生效。換貨不收費，代價是店員的時間和下架後到上架前的缺貨空窗。

## User Stories

### 發起換貨

1. 身為店長，我希望營業中也能在格位面板更換格位的商品，這樣冷門商品不必佔位一整天。
2. 身為店長，我希望營業中更換的商品不會立刻出現，而是由店員先下架舊商品、再上架新商品，這樣店裡的變化看起來合理。
3. 身為店長，我希望換貨不收費，代價只是店員的時間與一段缺貨空窗。
4. 身為店長，我希望同時可以有多個格位在換貨，不設上限，實際快慢由店員人數決定。
5. 身為店長，我希望營業中也能把格位改成不指定商品，一樣先下架再清空。
6. 身為店長，我希望營業中換貨的限制與準備階段相同：新商品必須已解鎖、類別必須符合陳列櫃（冷藏或常溫），不符合時被拒絕並看到原因。
7. 身為店長，我希望準備階段更換格位商品仍然立即生效，因為那時沒有顧客與店員在店裡。

### 下架之前

8. 身為店長，我希望下令換貨後、店員下架前，舊商品仍在架上照賣，這樣不會白白損失銷售。
9. 身為顧客，我希望在換貨中的格位仍能買到舊商品，直到它被下架。
10. 身為店長，我希望下架前不會再有人補舊商品，這樣不會白搬。
11. 身為店長，我希望下架前把格位改回原本的商品，就等於取消換貨。
12. 身為店長，我希望下架前改成第三種商品時，只會更新目標商品，不會重來。
13. 身為店長，我希望格位本來就是空的（陳列庫存為 0）時，換貨立即生效，因為沒有東西要下架。

### 下架與上架

14. 身為店長，我希望店員一趟就把格位上的舊商品全部取下，這樣換貨不會拖很久。
15. 身為店長，我希望店員取下舊商品的那一刻，格位就改成新商品而且是空的。
16. 身為店長，我希望下架的舊商品退回倉庫，保留原本的批次與送達日，之後可以再上架或照先進先出出貨。
17. 身為店長，我希望下架後，新商品照一般補貨上架；倉庫有新商品時會有店員去補。
18. 身為店長，我希望店員的工作優先順序是：有人排隊的收銀台 ＞ 派工 ＞ 下架 ＞ 一般補貨，這樣換貨不會害收銀大排長龍。
19. 身為顧客，我在下架後、上架前來找新商品的類別，會看到格位沒貨而算缺貨；這段空窗是換貨的代價。
20. 身為店長，我希望多位店員不會同時去下架同一個格位。

### 與派工的配合

21. 身為店長，我希望對換貨中、還沒下架的格位派工時，最近有空的店員會先去下架，再把新商品補滿，完成後才清除派工標記。
22. 身為店長，我希望換貨中的格位即使舊商品還滿架，也能派工。
23. 身為店長，我希望派工到換貨中的格位時，「倉庫沒有貨」是看新商品，而不是舊商品。

### 打烊與存檔

24. 身為店長，我希望打烊時還沒下架的換貨直接完成：舊商品退回倉庫、格位改成新商品。
25. 身為店長，我希望打烊時店員手上正搬著的舊商品一併退回倉庫，不會消失。
26. 身為店長，我希望隔天開店後，新商品照一般補貨上架。
27. 身為玩家，我希望營業中離開、重新載入後回到當天的準備階段，換貨不會殘留半套狀態。

### 其他規則看到的格位

28. 身為店長，我希望換貨中、下架前，所有「看格位賣什麼」的地方都算舊商品：顧客找商品、狀況「供應商出清」挑選陳列商品、架上的商品圖。
29. 身為店長，我希望下架後，以上這些都改算新商品。

### 畫面

30. 身為店長，我希望營業中點陳列櫃時，抽屜裡同時有派工與格位商品的選擇，這樣能在同一處決定。
31. 身為店長，我希望格位面板在換貨中顯示「換貨中：可樂 → 綠茶」，下架後恢復一般顯示。
32. 身為店長，我希望場景中換貨中的格位上方浮出 ⇄ 圖示，與既有的問題膠囊並存，這樣一眼看出哪些格位還在換。
33. 身為手機上的店長，我希望換貨的操作在手機抽屜與桌機面板都能使用。

## Implementation Decisions

### 模擬核心（sim）

- `Game` 仍是對外唯一入口（ADR 0001）。**不新增指令**：沿用「指定格位商品」指令，依階段決定行為：
  - 準備階段：與現在相同，立即生效（舊陳列庫存退回倉庫、格位改成新商品）。
  - 營業時段：發起換貨（ADR 0004）。驗證規則與準備階段相同（商品存在、類別已解鎖、陳列櫃類型符合）。
  - 其他階段：維持拒絕。
- 新增唯讀狀態：每個格位的換貨目標（下架後要改成的商品，可能是「不指定商品」）；沒有換貨時為空。格位面板與場景據此顯示。
- 換貨規則：
  - 格位陳列庫存為 0 時立即生效，不建立換貨。
  - 下架前改回目前的商品：取消換貨。改成其他商品：只更新換貨目標。
  - 下架前，該格位不列入一般補貨的候選。
- 下架是店員的新工作：走到格位的取用格 → 取下全部陳列庫存（此時格位改成換貨目標且為空、換貨結束）→ 搬到倉庫門 → 退回倉庫。取下所需步數與上架相當。
- 店員工作的優先順序：有人排隊的收銀台 ＞ 派工 ＞ 下架 ＞ 一般補貨。同一個格位的下架由一位店員認領，與補貨共用「已認領的格位」機制，避免重複。
- 派工與換貨：
  - 對換貨中的格位派工：店員先下架，再補滿新商品，完成後清除標記。
  - 派工的「格位已滿」檢查對換貨中的格位不適用；「倉庫沒有貨」改看換貨目標。
- 打烊時：所有換貨直接完成（舊陳列庫存退回倉庫、格位改成換貨目標）；店員手上搬的舊商品退回倉庫（現有的打烊清理已涵蓋搬運中的商品，需確認下架的商品也走同一路徑）。
- 其他讀取格位商品的地方（顧客找商品、供應商出清的前提與參數、補貨候選）在下架前看舊商品，下架後看新商品；由「格位目前的商品」自然得到，不需特別處理。

### 存檔（ADR 0002）

- 換貨只存在營業時段，打烊時一定完成；準備階段的快照不包含換貨，存檔格式與版本號不變。

### 介面（ui / render）

- 營業時段點陳列櫃：抽屜（手機）與面板（桌機）在派工之外加入格位商品的選擇，沿用準備階段的格位選單元件。
- 格位面板在換貨中顯示「換貨中：舊商品 → 新商品」；換成不指定商品時顯示「換貨中：舊商品 → 清空」。
- 場景：換貨中的格位所在那一格陳列櫃上方浮出 ⇄ 圖示，與問題膠囊錯開位置、並存。
- 介面只讀狀態、發指令，不直接改 sim（ADR 0001）。

### 平衡

- 固定平衡策略不使用換貨；`npm run balance` 的結果不應改變。

## Testing Decisions

- 好的測試只驗證外部行為：透過 `Game` 的指令、`tick`、唯讀狀態、每日結算與通知觀察結果，不檢查私有欄位。固定種子與固定步長，結果可重現。
- **`Game` 介面（主要）**：沿用 `dispatch.test.ts` 的寫法（擺好店面、跑到第 2 天、`tickResolving` 推進）。涵蓋：
  - 營業中指定格位商品會建立換貨而非立即生效；準備階段仍立即生效。
  - 下架前舊商品照賣、不被補貨；下架那一刻格位改成新商品且為空、倉庫多出舊商品；之後新商品被補上。
  - 陳列庫存為 0 時立即生效；改回原商品取消；改成第三種商品只更新目標；換成不指定商品。
  - 驗證錯誤（未解鎖、陳列櫃類型不符）在營業中同樣被拒。
  - 優先順序：有人排隊的收銀台優先於下架；派工優先於下架；下架優先於一般補貨。兩位店員不會同時下架同一格。
  - 派工到換貨中的格位：舊商品滿架也能派工；先下架再補滿新商品；倉庫沒有新商品時被拒。
  - 打烊時換貨直接完成，店員手上的舊商品退回倉庫；庫存總數在打烊前後守恆。
- **存檔**：沿用 `save.test.ts`：有未完成換貨的營業日打烊、進入準備階段後存讀檔，狀態相等，存檔版本號不變。
- **平衡**：既有平衡守門測試全部通過。
- ⇄ 圖示與面板文字維持手動驗證。

## Out of Scope

- 營業中擺設、移動、出售設施；營業中改售價、下一般進貨單、雇用與解雇（仍只在準備階段）。
- 換貨費用、換貨數量上限。
- 部分下架（只取下一部分舊商品）、指定由哪一位店員換貨。
- 每日結算記錄換貨。
- 平衡策略使用換貨。

## Further Notes

- 決策理由見 ADR 0004；詞彙「換貨」「下架」已加入 `CONTEXT.md`。
- 下架與補貨、派工共用店員的工作與「已認領的格位」機制，實作時優先擴充既有的店員工作流程，而不是另起一套。
