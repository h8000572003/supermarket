# 規格：麻煩（垃圾、老鼠、奧客）

Status: resolved

詞彙以 `CONTEXT.md` 為準（麻煩、垃圾、老鼠、奧客、派工、來客速率、滿意度、口碑、狀況）；架構依 ADR 0001（模擬與畫面分離）、0002（只在準備階段存檔）、0003（營業中只有暫時性指令）。本功能不新增 ADR：麻煩打烊即清除、不改存檔格式，容易反悔。

## Problem Statement

營業時段裡，店長能介入的只有限時特價、緊急叫貨、派工，以及偶爾跳出來、讓遊戲暫停的狀況。場上沒有需要店長「盯著畫面、即時反應」的東西，營業中常常只是看著時鐘走。

## Solution

新增**麻煩**：營業中出現在店內、不讓遊戲暫停的東西或人物，分為垃圾、老鼠、奧客。麻煩在場期間會降低來客速率，也降低店內顧客的滿意度。店員不會主動處理，店長點擊麻煩就是對它派工，最近有空的店員走過去處理；處理期間這位店員不收銀、不補貨。打烊時所有麻煩消失。及時處理的損失小，放著不管就一直流失客人。

## User Stories

### 共通

1. 身為店長，我希望麻煩出現時頭上有醒目圖示並播放音效，遊戲不暫停，這樣我能邊經營邊注意到。
2. 身為店長，我希望點擊（手機上是點一下）麻煩就派工，最近有空的店員會走過去處理，處理完自動恢復收銀與補貨。
3. 身為店長，我希望處理麻煩的派工和格位、收銀台的派工共用同時 2 個的名額；名額滿了點麻煩會提示「派工已滿」，這樣我得決定先處理哪個。
4. 身為店長，我希望能取消對麻煩的派工，和取消其他派工一樣。
5. 身為店長，我希望店員只有被派工才會處理麻煩，不會自己去撿垃圾或抓老鼠。
6. 身為店長，我希望每個在場的麻煩都讓來客速率乘上一個倍率（垃圾 ×0.95、老鼠 ×0.8、奧客 ×0.85，多個疊乘），處理掉就立刻恢復。
7. 身為店長，我希望顧客在店內期間，只要和某個麻煩同時在場過，離店時就為那個麻煩扣一次滿意度；同一個麻煩對同一位顧客只扣一次。
8. 身為店長，我希望打烊時所有麻煩直接消失，不會帶到隔天。
9. 身為店長，我希望處理麻煩的店員在處理期間不收銀、不補貨；如果他原本站在收銀台，那台收銀台暫時沒有店員。

### 垃圾

10. 身為店長，我希望顧客在店內時有小機率在走過的格子掉下垃圾，從第 1 個營業日起就會發生，客人越多垃圾越多。
11. 身為店長，我希望垃圾不擋路，也不會自己消失，店員清掃只要約 1 遊戲分鐘。

### 老鼠

12. 身為店長，我希望老鼠從倉庫門跑進店裡，在走道上隨機移動。
13. 身為店長，我希望被派去的店員要追到老鼠當下的位置，再花約 3 遊戲分鐘才能抓到。
14. 身為店長，我希望老鼠不吃商品，也不會自己離開。
15. 身為店長，我希望老鼠從第 3 個營業日起才會出現，每天最多 1 隻。

### 奧客

16. 身為店長，我希望奧客從入口進來，在店內四處走動抱怨，不買東西也不排隊。
17. 身為店長，我希望在奧客附近（約 3 格內）待過的顧客，離店時滿意度再多扣一次。
18. 身為店長，我希望奧客待一段長時間後會自己離開；派店員勸離約 5 遊戲分鐘，可讓他提早走。
19. 身為店長，我希望奧客從第 3 個營業日起才會出現，每天最多 1 位，而且他不算顧客，不計入顧客人數、滿意度平均與顧客類型統計。

### 每日結算

20. 身為店長，我希望每日結算多一行麻煩摘要：今天出現幾個、處理了幾個、累計在場多久，這樣我知道拖延的代價。

## Implementation Decisions

### 模擬核心（sim）

- 新增 `sim/nuisances/` 模組，以資料定義三種麻煩（種類 id、名稱、來客倍率、滿意度扣分、處理時間），與 `incidents/` 同一種寫法。新增種類時只加定義；需要新行為（移動、自行離開）時才改 `Game`。
- `Game` 維持唯一對外入口（ADR 0001）。新增唯讀的在場麻煩清單（id、種類、位置、出現時刻、是否已有人被派去），供畫面繪製與點擊。
- `DispatchTarget` 新增 `{ kind: 'nuisance'; nuisanceId }`。沿用 `dispatch` / `cancelDispatch` 與 `MAX_DISPATCHES = 2`。目標麻煩消失（處理完、奧客自行離開、打烊）時，標記由現有的「清除已完成派工」流程移除。
- 店員新增「處理麻煩」任務：走到目標位置，停留該種類的處理時間，結束時麻煩移除，店員恢復自動工作。老鼠會移動，所以店員走路途中要追蹤老鼠的最新位置（每次重新規劃路徑，或到達後若老鼠不在原處就再追）。
- 來客速率：在現有的倍率乘積（口碑、天氣、狀況的 `arrival-surge` 等）再乘上所有在場麻煩的倍率。
- 滿意度：每位顧客記下這次來店與哪些麻煩同時在場過（id 集合），以及是否在奧客附近待過；離店計算滿意度時，每個麻煩扣一次，奧客附近再扣一次。扣分數值放在麻煩定義裡，初值由平衡測試調整。
- 產生：
  - 垃圾：顧客每走過一格，有小機率在該格掉垃圾（只掉在走道格，不掉在設施或取用格以外的不可走格上）。用模擬的種子亂數，結果可重現。
  - 老鼠、奧客：開店排程時，第 3 個營業日起各以一定機率排定今天出現的時刻（每天最多各 1 次），與狀況的排程分開、互不影響。
- 奧客是一種新的移動代理，不是 `Customer`：不帶購物清單、不進隊伍、不計入顧客統計。到了自行離開的時刻，或勸離處理完成，就走向入口離店；走向出口期間不再算在場（不再降來客速率或扣分）。
- 打烊（`closeStore`）時清除所有麻煩、相關派工與處理中的店員任務。
- 新增 `GameEvent`：麻煩出現、麻煩處理完成，供音效與畫面使用。
- 存檔：麻煩只存在於營業時段，`GameSnapshot` 不變，不需遷移（ADR 0002）。

### 每日結算

- `DailyReport` 新增麻煩摘要：各種類的出現數、處理數，以及全部麻煩累計在場的遊戲分鐘數（打烊清除與奧客自行離開的，在場時間算到消失為止）。每日結算不在存檔裡，格式不受影響。

### 介面（ui / render）

- 場景繪製垃圾、老鼠、奧客的 sprite，以及頭上的醒目圖示；已有店員被派去的麻煩，圖示改成「處理中」樣式。
- 點擊判定（`render/pick.ts`）能點到麻煩，點中就呼叫 `dispatch`；已派工的再點一次就取消。名額滿時顯示「派工已滿」。麻煩的點擊優先於它底下的格位或設施。
- 音效：麻煩出現、處理完成。
- 每日結算畫面加上麻煩摘要一行。
- 介面只讀狀態、發指令，不直接改 sim（ADR 0001）。

### 平衡

- 平衡策略（`balance/strategies.ts`）的「標準經營」在麻煩出現時立刻派工處理；派工名額滿時等有空位再派。
- 既有三條平衡斷言照樣通過，必要時調整麻煩的機率與倍率，而不是放寬斷言。
- 新增策略「放著不管」：除了不處理麻煩，其他與標準經營相同；斷言它的累計營收明顯低於標準經營。

## Testing Decisions

- 好的測試只驗證外部行為：透過 `Game` 的指令、`tick`、唯讀狀態、`GameEvent` 與每日結算觀察，不檢查私有欄位。固定種子、固定步長，結果可重現。需要特定麻煩時，用測試輔助（`test-helpers.ts`）在指定位置放置麻煩，與現有狀況測試的做法相同。
- **`Game` 介面**（沿用 `dispatch.test.ts`、`incident-effects.test.ts` 的寫法）：
  - 對麻煩派工後，店員走過去，經過處理時間後麻煩消失，派工標記清除，店員恢復收銀與補貨。
  - 派工名額共用：已有 2 個派工時，對麻煩派工回傳 `dispatch-full`；可取消對麻煩的派工。
  - 沒有派工時，店員不會處理麻煩。
  - 麻煩在場時來客速率乘上對應倍率，多個疊乘；處理後恢復。
  - 與麻煩同時在場過的顧客滿意度扣分，同一個麻煩只扣一次；麻煩出現前已離店的顧客不受影響；奧客附近的顧客再多扣一次。
  - 老鼠會移動，店員能追到並抓到。
  - 奧客不計入顧客統計，到時間會自行離開，勸離後提早離開。
  - 老鼠、奧客第 1、2 天不出現，第 3 天起每天最多各 1 次。
  - 打烊後沒有麻煩、沒有麻煩派工。
  - 每日結算的麻煩摘要數字正確。
- **存檔**：營業中有麻煩時存讀檔（回到準備階段）後沒有麻煩，既有存檔測試照樣通過。
- **平衡**：既有斷言通過，新增「放著不管比較差」斷言。
- sprite、圖示、音效、點擊手感維持手動驗證。

## Out of Scope

- 老鼠咬壞或吃掉商品。
- 店員主動處理麻煩、可設定的自動處理。
- 麻煩獨立的派工名額或提高 `MAX_DISPATCHES`。
- 麻煩延續到隔天、寫入存檔。
- 預防設施（垃圾桶、捕鼠器、保全）與相關里程碑。
- 其他種類的麻煩。

## Further Notes

- 詞彙「麻煩」「垃圾」「老鼠」「奧客」已加入 `CONTEXT.md`。「狀況」維持原義：會暫停、要擇一選項；麻煩不暫停、靠派工處理。
- 數值（來客倍率、扣分、機率、處理時間）是初值，以平衡測試為準調整。
